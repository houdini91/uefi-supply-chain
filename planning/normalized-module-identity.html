Normalized Module Identity

Where a rebase-0 module digest belongs in CycloneDX, SPDX 3.0, coSWID and in-toto — and why “just define a sha256-norm algorithm” is right in exactly one of them.

2026-09-03anchor D = sha256:7965c317…62fb8f37 OVMF_CODE.fd · 122/122 reconcileddrafted, nothing filed

The answer

The normalized digest is an identity, not a hash algorithm — everywhere it is a catalogue attribute. It is an algorithm-shaped key in exactly one place: the in-toto digest map, where equality-matching is the whole point. Both of your instincts were right; they apply to different layers.

Catalogue layer

SBOM formats

CycloneDX, SPDX 3.0, coSWID. A digest here describes a component. Model the normalization as an identifier or a class; leave the algorithm slot a plain primitive. Eight independent precedents, zero exceptions.

Matching layer

in-toto / your VSA

DigestSet is a flat equality map. in-toto explicitly rejected a separate “kind” field — citing Authenticode — because it would complicate match semantics. Here a new key name is the blessed pattern.

The question

Why not just define sha256-norm and use the normal hash field?

Because both SBOM formats close the door mechanically, and the registry that coSWID depends on says the preimage is out of its scope. This isn’t taste — it’s three validators and one RFC.

Two details are worse than they look. In SPDX the JSON-LD context puts a scoped @vocab on algorithm, so "algorithm":"sha256Norm" silently expands into SPDX’s own namespace (…/terms/Core/HashAlgorithm/sha256Norm) before failing sh:in — you cannot even express a foreign algorithm IRI through the shorthand. And in coSWID, hash-entry is a fixed two-element array, so nothing can ride inside it at all:

hash-entry = [ hash-alg-id: int, hash-value: bytes ]      ; fixed — nothing fits inside

file-entry = {
  filesystem-item, ? size => uint, ? file-version => text,
  ? hash => hash-entry,
  * $$file-extension,          <-- the only door, and it is a real one
  global-attributes,
}
“Other than in the aforementioned special case where public keys are used, we do not specify the hash function input here. Other specifications are expected to define this.” RFC 6920 §2 — the IANA Named Information Hash Algorithm Registry

That is the registry underneath coSWID putting the preimage explicitly outside its remit. All 20 entries transform the output (truncation, XOF parameters); not one transforms the input. RFC 6920 even had its own canonicalization rule — hash a public key as an X.509 SubjectPublicKeyInfo — and put it in prose rather than mint an spki-sha-256 entry. Registration is Expert Review, so the realistic response is “define the normalization in your spec and use sha-256.”

Evidence

How the ecosystem has answered this before

Every one of these is a digest over a transformed preimage — structurally your case. Authenticode is the closest analogue of all: a PE hash that deliberately excludes the checksum and certificate table, exactly the kind of surgery canon_unrebase() performs.

Eight to one — and the one dissenter documents its own reasoning. in-toto issue #28 raised precisely your question, naming Authenticode, and rejected a separate kind field to avoid “needing any fancy comparison logic.” That rationale is specific to a map whose job is equality matching. An SBOM hash is a catalogue attribute, so it doesn’t carry over — which is why the split at the top of this page is convention, not contradiction.

Worth knowing when someone pushes back: SPDX’s own architect proposed a per-scheme IntegrityMethod subclass for gitoid and then withdrew it — “I do not believe that throwing new properties on for each new approach is a tenable or scalable solution” — in favour of one class plus an extensible vocabulary “which can be expanded in the future, with no breaking changes.” Nobody ever proposed gitoid as a HashAlgorithm value. That option was never on the table.

Options

Three honest routes

A · New algorithm id rejected

  • + Simplest mental model; nothing new to invent
  • + Distinct key sidesteps protobom’s one-hash-per-algorithm collision for free
  • − Fails CycloneDX and SPDX schema validation outright
  • − IANA would redirect on scoping, not crypto, grounds
  • − Adding one CDX enum value took ~16 months (Streebog, 2024-06 → 2025-10)
  • − SPDX has added exactly one value in three years, as an oversight fix

Dead in the SBOM layer. Correct in in-toto.

B · Method qualifier overbuilt

  • + Fully general; separates primitive from preimage cleanly
  • − Nowhere to put it: CDX additionalProperties:false, SPDX IntegrityMethod has only comment
  • − Needs new fields in four places at once
  • − A third-party SPDX subclass passes SHACL but fails the JSON schema — it looks like it works, then doesn’t

Where I was drifting. The ecosystem never chose it.

C · Named identity recommended

  • + Exactly what gitoid, SWHID, cdhash and Authenticode all did
  • + Each format already has the slot — no new fields anywhere
  • + The definition lives in your profile doc, so nothing ossifies into a spec
  • + Extensible vocabularies are designed to grow “with no breaking changes”
  • − Needs one small versioned profile document written first
  • − Still a vocabulary entry per format, on each one’s own clock

One identity, expressed in each layer’s own idiom.

The zero-cost option is still live. Nothing breaks today if you document genfw-rebase-0 as a convention and change no spec: the gate is green, 122/122 reconciles, the same-GUID swap DENYs. The injured party is a third party producing a normalized hash for someone else’s verifier without coordination — and that party does not exist yet. Route C is worth doing because you want the ecosystem to have the slot, not because your pipeline needs it. Say that plainly rather than manufacturing urgency.

The proposal

One identity, four expressions

Define the transformation once, in a short versioned profile you own — preimage (EFI_SECTION_PE32 payload, section header stripped), the un-rebase (HIGHLOW/DIR64 only, anything else fails closed), the three zeroed header fields as byte patches rather than a re-serialize, then SHA-256. Publish test vectors. Then carry the resulting identity in whatever slot each format already provides.

coSWID — the extension socket

Richard’s call

Nothing can go inside hash-entry (fixed array), and hash-alg-id stays 1 = sha-256 — RFC 9393 says other algorithms MUST NOT be used. So the method rides as a sibling key via $$file-extension. A negative index is private-use and needs no registration, which makes it the right way to prototype before asking for anything.

file-entry = {
  fs-name: "PeiCore",
  hash: [ 1, h'1348ff9c…681051' ],   ; alg-id 1 = sha-256, unchanged
  ? -1 => "uefi-pe-rebase0.v1",        ; $$file-extension — private use (-256..-1)
}

in-toto DigestSet — your VSA

already yours

The one layer where your original instinct is the blessed pattern: a new key name beside sha256, exactly as gitBlob and dirHash do. No registration, no permission — in-toto asks only that a new algorithm document how its value is encoded.

"subject": [{
  "name": "PeiCore",
  "digest": {
    "sha256":  "…",                              <-- as-found, differs (rebased)
    "uefi-pe-rebase0-v1": "1348ff9c…681051"                 <-- normalized identity
  }
}]
uefi-pe-rebase0.v1 is the identifier used in this repo; the ecosystem spelling is open. The scheme name, its version segment and whether the transformation belongs in the name at all are community decisions, not ones to settle unilaterally — gitoid chose gitoid:blob:sha256:… and SWHID chose swh:1:cnt:…, so there is precedent for both styles. What matters is that the value is a URI (SPDX requires anyURI) and that the profile document defining the transformation is what the identifier points at.

The other half

How this connects to CHIPSEC

These are not two efforts. CHIPSEC issue #2843 is the observed end of the same identity that the SBOM work carries on the declared end — one profile, computed at build and recomputed from the shipped image, compared. Framing the CHIPSEC PR as “emit the normalized module identity” rather than “add a hash variant” is both a stronger pitch and a smaller commitment: the definition lives in the profile document, so CHIPSEC implements a spec rather than becoming one. That directly answers Richard’s ossification objection — the normal form does not get frozen into anyone’s code, in either project.

Nothing about CHIPSEC waits on the SBOM work, or the reverse. scan_image already has its own baseline — a golden efilist.json from generate — and today that loop is layout-bound, because modules are hashed as-found after relocation. A normalized value fixes CHIPSEC’s own workflow with no SBOM in the picture, which is why npmitche could say “I like the idea of simply adding a sha256_norm field” without asking what consumes it. The SBOM alignment is the second motivation, not the load-bearing one. Both threads need the profile; neither needs the other.

One sequencing constraint is real and it is technical, not strategic: write the profile with byte-patch normalization before the CHIPSEC PR ships. The normalization is now byte patches at documented offsets (done 2026-09-03), with a dependency-free second implementation and runnable vectors (done 2026-09-04) — so the CHIPSEC branch implements a written profile rather than becoming its definition.
